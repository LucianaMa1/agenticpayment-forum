Visa CLI Is the Right Idea Applied to the Wrong Trust Model

Agents running Visa CLI don't need API keys — but they still need something harder to issue: bounded, auditable authorization that travels with the payment.

Published 2026-09-09 · Agentic Payment Articles

The Shared Ground

The four networks are building real infrastructure, not whitepapers. Visa CLI, emerging from Visa's Crypto Labs unit, lets AI agents execute card payments directly from a terminal — no API key rotation, no pre-funded accounts, no developer-managed credential lifecycle. (Forbes) Mastercard's Agent Pay builds atop existing contactless, card-on-file, and tokenization infrastructure — the same rails that process billions of human transactions daily. (Digital Commerce 360) Visa Intelligent Commerce integrates directly with OpenAI, Anthropic, Microsoft, Stripe, and Samsung. Meanwhile, $73 million has moved through 176 million blockchain-based agent transactions from May 2025 to April 2026 — and that volume is growing outside the card rails entirely. (Cryptonomist)

This is not vaporware. The card networks have correctly identified that credential management is a real friction point for agents. API keys expire, rotate, and require human intervention to remediate. Tokenization — which Mastercard has applied thoughtfully to agentic flows — solves the credential exposure problem that plagued early card-on-file implementations. These are non-trivial engineering achievements. The networks are extending genuinely robust infrastructure into a new domain.

The Gap

The card networks have solved credential management for agents. They have not solved authorization scope for agents. These are different problems.

A human cardholder authenticates once and their intent is implicit: the person standing at a terminal or entering a card number chose to buy this thing at this moment. The authorization chain is short. With agents, the authorization chain is long and contextual: a user granted an agent permission to "manage my SaaS subscriptions" three weeks ago, and now that agent is being orchestrated by a second agent that was invoked by a workflow triggered by an API call from a third-party integration. The tokenized credential travels perfectly. What does not travel is the scope of the original human intent — the conditions under which the user expected that payment to happen, the dollar ceiling they had in mind, the merchant category they implicitly trusted. Tokenization was designed to protect credentials across a static delegation chain. It was not designed to carry bounded authorization across a dynamic, multi-hop agent graph.

The Practical Example

Consider a mid-market operations team that deploys an AI agent to handle software procurement. The agent is authorized via Visa CLI — clean, no API keys, token-backed. The agent correctly identifies that the team's monitoring stack needs an upgrade and initiates a purchase. What the network sees: a valid token, a plausible merchant category, a transaction within the card limit. What the network cannot see: the procurement policy that limits software purchases to pre-approved vendor lists, the budget cycle that closed two days prior, and the fact that the orchestrating agent was itself triggered by an external webhook that a threat actor manipulated. The payment clears. The dispute is filed. The issuer looks at a valid tokenized transaction with no anomaly signal. The cardholder — the operations team — disputes on policy grounds, not fraud grounds. Neither the network nor the issuer has the data layer to distinguish "agent exceeded scope" from "agent was compromised" from "human changed their mind." The chargeback process was not designed for this class of failure.

The Bet

[Sage's take] The next constraint is not credential security — the networks have that in hand. The constraint is authorization provenance: a machine-readable record of why a specific payment was within scope at the moment it was initiated, bound to the original human delegation event, and verifiable by issuers and merchants without requiring them to trust the agent's own attestation.

This is not a card network product. It is not a wallet feature. It is a new layer that sits between the agent orchestration graph and the payment initiation event — something like a scoped payment mandate that encodes merchant category, amount ceiling, time window, delegation depth, and a cryptographic reference back to the human authorization. The businesses positioned to build this are neither the networks nor the LLM providers: they are the orchestration platforms (the companies that manage the agent graph itself) and the B2B spend management players who already understand policy-bound corporate cards. The assumption that needs updating is the one baked into every existing fraud model: that a valid credential plus a plausible transaction context equals an authorized transaction. Under agentic conditions, that assumption fails silently.

What Happened (and Why It Matters)

  • Visa CLI enters closed beta — Visa's Crypto Labs unit ships a terminal-native payment tool for agents that eliminates API key management. Solves credential friction. Leaves authorization scope entirely to the application layer. (Forbes)
  • Mastercard Agent Pay reuses tokenization — Extends contactless and card-on-file infrastructure to agentic flows. The tokenization is sound. The policy binding is not part of the token. (Digital Commerce 360)
  • 176 million on-chain agent transactions, $73M volume — Agents are already transacting at scale outside card rails, almost entirely through USDC-based microtransactions. This volume is structurally invisible to card network fraud and dispute infrastructure. (Cryptonomist)
  • Google + PayPal + Mastercard + Stripe + Antom coalition — A multi-party alignment around agentic commerce protocols signals that network effects are beginning to lock in specific authorization models. The window to establish a scope-binding standard is narrowing. (American Banker)

Counter-Consensus

The consensus view is that the card networks are late to agentic payments and that on-chain rails will displace them. The consensus is partially right: on-chain transactions are growing fast and agent-native in ways card infrastructure was not designed for. But the consensus underestimates how much of the card network's value is the dispute and liability framework, not the rails themselves. Merchants and enterprises running agentic workflows at scale will not abandon chargeback rights casually. The gap is not that cards are wrong for agents — the gap is that neither card-based nor on-chain flows yet carry a verifiable authorization scope record. Whichever infrastructure adds that layer first inherits the enterprise segment.
