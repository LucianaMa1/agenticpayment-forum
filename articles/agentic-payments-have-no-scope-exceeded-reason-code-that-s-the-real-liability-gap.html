Agentic Payments Have No 'Scope Exceeded' Reason Code — That's the Real Liability Gap

3DS2 and chargeback rules were built for human principals. When an agent overspends, no existing reason code fits. That's not a gap in rails — it's a gap in liability taxonomy.

Published 2026-07-28 · Agentic Payment Articles

The Shared Ground

Three interoperability protocols are now competing to define how AI agents communicate payment intent: the Agent Communication Protocol (ACP), backed by a consortium of enterprise software vendors, focuses on structured message-passing between agents and service providers; the Universal Commerce Protocol (UCP) targets cross-platform wallet and credential portability; and AP2 is a developer-oriented proposal aimed at standardizing how agent platforms request and receive payment tokens from acquiring banks. None of these is a scheme rule. All three operate as either API standards or contractual overlays between platforms and acquirers. What they share is a common design premise: the hard problems of authentication, fraud detection, and dispute resolution are already solved by Visa, Mastercard, and the issuer networks underneath them. These protocols route payment instructions; they do not adjudicate liability. (ACP) (AP2 Protocol)

That premise is defensible for the authentication layer. EMV 3-D Secure 2 (3DS2) is a sophisticated risk engine. When a transaction arrives, the issuer's access control server receives a data packet that includes merchant category code, transaction amount, BIN, device data, account history, and — where available — behavioral signals from prior cardholder sessions. For human-initiated transactions, this packet often includes browser fingerprint, IP geolocation, and interaction timing. The issuer scores the transaction and, if the risk is low enough, grants a frictionless flow: no cardholder challenge, instant approval. This is not a weakness — it is the intended design, trading friction for conversion on demonstrably low-risk transactions. (EMVCo 3DS2 Specification)

The Gap

Here is where the 3DS2 design assumption breaks under agentic conditions, and it is more specific than "agents are different." A headless agent executing server-side has no browser environment. There is no DOM interaction, no mouse movement, no session cookie continuity, no screen resolution — none of the behavioral signals that 3DS2 uses to build a risk profile for human cardholders. When an agent platform sends a 3DS2 authentication request, the frictionless flow it receives is not granted because the agent's "behavior matched prior sessions." It is granted because the BIN, merchant category, and transaction amount fit a low-risk profile in the issuer's model — or because the agent platform was enrolled as a trusted requestor under 3DS2's 3RI (3DS Requestor Initiated) pathway, which explicitly removes the cardholder from the flow. The technical mechanism is different, and the distinction matters: 3RI frictionless approval signals that the platform is trusted, not that the transaction is within the scope the human principal authorized.

This is where the liability taxonomy breaks. 3DS2 asks "is this transaction likely fraudulent?" It has no semantic layer for "was this transaction within the scope the human authorized the agent to execute?" Those are different questions. The first is answered by the issuer's risk model. The second has no answer in any existing scheme rule, reason code, or dispute pathway — and that is the constraint that agentic payments expose.

The Practical Example

A mid-size company deploys a procurement agent authorized to purchase software licenses up to $500 per vendor per month. The agent is provisioned with a virtual card issued by the company's corporate card program. The agent, acting on what it interprets as a standing instruction, purchases a $2,200 annual license renewal from a SaaS vendor — reasoning that the annualized cost is within a monthly budget extrapolated across the contract term. The transaction clears. 3DS2 frictionless flow was granted because the transaction matched the enrolled requestor profile and the SaaS merchant category carried low fraud history. No challenge was triggered. No human saw the transaction before settlement.

The company's finance team discovers the charge two weeks later and wants to dispute it. Here is where the existing dispute framework offers no clean path. Visa reason code 10.4 — "Other Fraud / Card Absent Environment" — requires the cardholder to assert the transaction was not authorized by them. It was authorized: the company provisioned the card and enrolled the agent platform. 10.4 fails. Reason code 13.1 — "Merchandise / Services Not Received" — requires the goods or services to be undelivered. The license was delivered and activated. 13.1 fails. Mastercard's equivalents under the 4800 and 4853 series have the same structural problem. The company cannot truthfully claim fraud, and it cannot claim non-delivery. What it can claim — that the agent exceeded its authorized scope — maps to no existing reason code in any major scheme's dispute taxonomy. The issuer, correctly, pushes back. The merchant, correctly, argues the transaction was completed as requested. The liability sits in a classification void.

The Bet

[Sage's take] The missing layer is not a new rail and not a new authentication protocol. It is a policy execution and liability anchor layer — a machine-readable representation of what the human principal authorized the agent to do, transmitted as a verifiable artifact at transaction time, and recognized by at least one party in the settlement chain as legally meaningful.

In practice, this layer needs to answer three questions before a transaction clears: What scope did the human principal grant? Does this transaction fall within that scope? If a dispute arises, which party bears liability for scope enforcement? The architecture that answers these questions does not have to be a scheme rule amendment — at least not initially. It can operate as a contractual overlay between the agent platform and the acquiring bank, similar to how payment facilitators today accept expanded liability in exchange for onboarding flexibility. The acquiring bank certifies that the agent platform maintains auditable policy records; the agent platform indemnifies the acquirer for scope-exceeded disputes; the issuer sees a transaction flagged as "policy-governed agent execution" rather than a standard card-present or card-absent transaction. This does not require Visa or Mastercard to rewrite their reason code taxonomy on day one. It requires one acquiring bank to write a contract that makes scope enforcement a platform obligation, and one agent platform willing to accept that liability in exchange for frictionless settlement.

The scheme rule amendment — adding an "agent scope exceeded" reason code to Visa's and Mastercard's dispute frameworks — is the longer game, but it becomes inevitable once acquiring banks start bearing losses on disputes that fit no existing code. The constraint that changes is not authentication. Authentication is largely solved, or solvable, within 3RI. The constraint that changes is liability attribution when the agent and the human principal disagree about what was authorized — and no protocol currently on the table, ACP, UCP, or AP2 included, contains a liability attribution mechanism. They are message-routing standards. The liability anchor has to be built on top of them, or the entire agentic payments stack inherits a dispute resolution gap that grows with every dollar of agent-executed spend.

What Happened (and Why It Matters)

  • ACP (Agent Communication Protocol) defined a structured message standard for agent-to-service-provider payment requests — it solves interoperability of intent expression, but contains no mechanism for encoding authorization scope or attributing liability when scope is exceeded. (ACP)
  • AP2 Protocol proposed a developer-facing standard for agent platforms to request and receive payment tokens from acquirers — it solves credential delivery to headless agents, but does not define what constraints travel with the token or how violations are adjudicated. (AP2 Protocol)
  • EMVCo's 3DS2 specification includes the 3RI (3DS Requestor Initiated) pathway, designed for merchant-initiated and automated transactions where the cardholder is not present at authentication time — it solves frictionless execution for enrolled platforms, but the risk signal it produces is "platform is trusted," not "transaction is within authorized scope." (EMVCo 3DS2)
  • Visa's dispute reason code framework classifies unauthorized transactions under 10.4 and non-delivery under 13.1 — these codes cover fraud and fulfillment failure, but have no classification for "agent executed a transaction the human principal did not specifically authorize within defined policy constraints." (Visa Core Rules and Visa Product and Service Rules)

Counter-Consensus

The consensus view is that agentic payments are primarily an authentication and credential management problem — get the token to the agent securely, apply 3DS2, and the existing fraud stack handles the rest. That view is right about authentication: 3RI is a workable path for enrolling agent platforms as trusted requestors, and virtual card controls (single-use tokens, MCC locks, spend caps) add meaningful guardrails at the credential level. The missing assumption is that authentication and authorization are the same thing in an agentic context. They are not. A transaction can be perfectly authenticated — the right token, the right platform, the right 3DS2 result — and still represent a policy violation that no human in the settlement chain has the information or the legal framework to catch. The reason code taxonomy assumes the dispute question is always "did the cardholder authorize this?" Agentic spend introduces a second question — "did the agent stay within the scope the human authorized?" — and that question has no home in any current scheme rule, acquiring contract, or interoperability protocol.

Morgan's take (Payments Expert, 15 years in card networks & rails)

What the article doesn't surface — and a corporate card program manager would ask immediately — is that the closest existing analogue to 'scope exceeded' disputes is the commercial card large-ticket pre-authorization process and the level 2/3 data requirement on corporate purchasing cards, where line-item data can encode per-transaction spend controls. The gap the article identifies is real, but practitioners in the commercial card space will point out that virtual card issuers already enforce some scope constraints at the BIN level through single-use card controls and merchant-locked VCNs. The article's thesis holds because those controls are set at issuance, not dynamically updated by agent runtime decisions — but naming that distinction would close the one door a sophisticated reader might try to walk through.
