The Gap None of Them Have Solved: Runtime Scope Negotiation in Agentic Payments

Visa, Mastercard, and Cloudflare have all published delegated-auth specs. None of them operate at agent runtime speed, asynchronously, mid-task. That gap is the constraint.

Published 2026-08-07 · Agentic Payment Articles

The Shared Ground

Three of the most credible infrastructure players in payments have now published explicit positions on agentic authorization. Mastercard's Agent Pay introduces a delegated credential model that allows a human cardholder to pre-authorize an AI agent to transact on their behalf, with spend controls and merchant-category constraints baked into the credential at issuance. (Mastercard Newsroom) Visa's Intelligent Commerce program follows a structurally similar path: tokenized agent credentials, scoped permissions, and a delegated authorization framework intended to let agents spend within human-defined rails. (Visa Intelligent Commerce) Cloudflare has entered from the infrastructure side, announcing an AI Wallet and payment primitive designed to let agents hold and spend stablecoins or fiat balances without requiring a human to re-enter the authorization loop at each transaction. (Cloudflare Blog)

These are serious efforts from serious organizations, and they deserve to be understood on their own terms before being challenged. Mastercard and Visa are not bolting AI onto legacy rails and calling it innovation. Both specs recognize that agents cannot use card-present flows, that cardholder verification methods designed for humans do not transfer cleanly to software, and that delegated authority requires a new credential primitive — not just a stored card token. Cloudflare is solving a different but related problem: that agents operating across APIs and services need a payment primitive that is native to the request-response model of the web, not retrofitted from a point-of-sale paradigm. The shared logic across all three is correct: agentic payments require scoped, delegated, machine-readable authorization. The existing system solves the issuance and scoping problem. The question is what it does not yet solve.

The Gap

Both Visa's Intelligent Commerce spec and Mastercard's Agent Pay documentation describe delegated authorization flows that allow scope updates — a credential can be refreshed to reflect changed permissions. That is a real capability and it matters. But the refresh cycle in both architectures operates on a human-initiated or session-bounded cadence. A cardholder, or a cardholder's application, triggers the refresh. The new scope is then available for subsequent transactions. What neither architecture currently supports is asynchronous, mid-task scope expansion requested by the agent itself at runtime — without pausing the task, without surfacing a human approval prompt, and without waiting for a session boundary to expire and reset.

This is not a minor implementation gap. It is a structural one. The existing delegated-auth model assumes that the scope of an agent's authority is knowable before the task begins, or that the task can be paused while a human updates it. Agentic tasks break that assumption in a specific way: the new authorization requirement is discovered by the agent mid-execution, as a consequence of decisions made earlier in the same task, in a context that did not exist when the original credential was issued. The scope that was correct at issuance is no longer correct at runtime, and no part of the current infrastructure has a protocol for the agent to request, negotiate, and receive an updated authorization scope in real time, asynchronously, without human intervention at that moment.

The Practical Example

A corporate travel agent is authorized to book flights and hotels up to $4,000 per trip for a specific employee. The employee asks the agent to book a trip to a conference. Midway through the booking flow, the agent discovers that all hotels within the approved per-night rate are sold out within 15 miles of the venue. The only available options either exceed the rate cap or require a refundable deposit — an incidental hold, which is a pre-authorization, not a purchase authorization — that the agent's credential does not cover because incidental holds were not anticipated when the scope was defined.

Here is where the gap becomes concrete. Visa's and Mastercard's credential refresh flows would, in principle, allow the scope to be updated to include a higher rate or incidental hold authorization. But that refresh requires a human to initiate it — or requires the agent to surface the conflict, halt the booking, wait for human input, receive a new credential, and then resume. In a task that spans multiple API calls, holds locks on inventory, and operates across a reservation system with session timeouts, that pause is not a minor inconvenience. It is a task failure. The practical effect is that the agent either exceeds its authorization and creates a dispute liability, abandons the task and returns an incomplete result, or — in a system designed to avoid both — surfaces an error that the human now has to resolve manually, which is precisely the outcome agentic systems are supposed to eliminate. The missing layer is a runtime negotiation protocol: a structured, authenticated, auditable channel through which an agent can say, mid-task, 'my current scope is insufficient for a decision I have encountered — here is the decision, here is what I need, here is the context' and receive a real-time authorization update without requiring a human to be present at that moment.

The Bet

[Sage's take] The competitive question is not which of these three players has the best delegated-auth spec at issuance. Mastercard and Visa are roughly equivalent in structural sophistication at the credential layer, and Cloudflare is solving a different segment of the problem. The competitive question is which player is architecturally closest to owning the runtime authorization layer — the loop that operates after issuance, mid-task, at agent speed.

Cloudflare has a structural advantage here that is underappreciated in payments circles. Its infrastructure sits at the request layer — between agents and APIs — which is exactly where runtime authorization decisions surface. A payment primitive that lives at that layer can, in principle, observe the task context, evaluate the scope conflict, and mediate a real-time authorization update without requiring a round-trip to a human session. Mastercard and Visa, by contrast, are working from the credential issuance layer outward. They can describe what an updated credential should look like; they do not yet have infrastructure at the runtime request layer to detect when an update is needed and broker it in real time. The player that builds the runtime negotiation protocol — the authenticated, auditable channel for mid-task scope expansion — will own the highest-value layer in agentic payments infrastructure. Right now, Cloudflare is closest to the right position in the stack, but has not yet shipped that capability. Mastercard and Visa have the scheme authority to make the credential valid, but not yet the runtime presence to negotiate it dynamically. The gap is open, and it will not stay open.

What Happened (and Why It Matters)

  • Mastercard launches Agent Pay — Introduces delegated credential infrastructure allowing human cardholders to authorize AI agents with scoped spend controls. Solves the issuance and initial scoping problem. Does not yet support asynchronous, agent-initiated scope expansion mid-task. (Mastercard Newsroom)
  • Visa publishes Intelligent Commerce spec — Tokenized agent credentials with delegated authorization and scope-refresh capability. Refresh cycle is human-initiated or session-bounded, not agent-runtime-speed. The spec describes the right primitive; the cadence is the constraint. (Visa Intelligent Commerce)
  • Cloudflare ships AI Gateway as Payment Gateway — Positions infrastructure-layer payment primitives for agents operating across APIs. Structurally closest to the runtime request layer where mid-task authorization conflicts surface. Has not yet shipped a runtime scope negotiation protocol. (Cloudflare Blog)

Counter-Consensus

The consensus view in payments is that delegated authorization — scoped credentials issued before a task begins, with refresh flows available — is the correct and sufficient architecture for agentic payments. That consensus is right about the issuance layer. Scoped, tokenized, delegated credentials are genuinely better than stored card numbers or session-level tokens for agents, and the work Mastercard and Visa have done to define this primitive is not incremental — it is a real architectural advance. The missing assumption is that agent tasks are predictable enough at issuance time for a pre-defined scope to remain valid through execution. The constraint that changes under agentic conditions is not the credential format — it is the moment of authorization. When the authorization requirement is discovered mid-task, by the agent, as a consequence of its own reasoning, the pre-issuance scope model requires the task to pause for human re-entry. That pause is the failure mode the industry has not yet designed around.

Morgan's take (Payments Expert, 15 years in card networks & rails)

The liability question is where this gap actually bites hardest in practice: under current scheme rules, if an agent expands its own scope and a transaction is later disputed, there is no clean liability assignment — the issuer approved a credential, the merchant processed a transaction that exceeded that credential's defined scope, and the acquiring bank is holding the exposure. I'd want to see the article name that, because that's the real reason the schemes haven't shipped runtime scope negotiation: it's not a technical problem, it's an indemnification problem nobody has agreed to sign.
