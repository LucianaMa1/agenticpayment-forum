The Real Agentic Payments Battle Is Over the Decision Loop, Not the Rails

Visa, Mastercard, and Google each solved a different layer of agentic payments. The missing layer is cross-network authorization metadata — and no scheme standard carries it yet.

Published 2026-08-24 · Agentic Payment Articles

The Shared Ground

In April 2025, Visa and Mastercard launched their agentic payment credentials within weeks of each other — Visa's Intelligent Commerce program and Mastercard's Agent Pay, both introducing tokenized, programmable credentials designed for non-human-initiated transactions. (Visa) (Mastercard) These are not marketing rebrands. Visa's program issues tokenized credentials with merchant-category and spend-ceiling constraints baked in at provisioning. Mastercard's Agentic Tokens carry similar delegation logic, with cryptographic binding to a specific agent principal. The card schemes understood early that the existing EMV token model — designed for device-bound human authentication — would break under agentic delegation, because the delegator and transactor are now different entities with potentially different risk profiles. Tokenization solves the card-not-present fraud surface. Spend controls solve the authorization-scope problem. These are real, necessary contributions.

Several months later, in September 2025, Google launched Agent2Agent Protocol (AP2) with 60+ integration partners, establishing a cross-agent communication standard that allows AI agents from different vendors to negotiate tasks, delegate subtasks, and share context. (Google) In April 2026, Google donated AP2 to the FIDO Alliance for stewardship. (FIDO Alliance) That donation matters structurally: FIDO already governs the device-attestation layer that Mastercard and Visa depend on for token security. AP2's move into the FIDO umbrella creates the possibility — not yet the reality — that agent identity attestation and payment credential delegation could share a common trust root. But that possibility also surfaces the timeline gap: AP2 arrived months after the scheme launches, not simultaneously. Visa and Mastercard built their agentic credential models before a cross-agent communication standard existed. That sequence matters for understanding what each layer can and cannot see.

The Gap

The existing system solves authorization scope (spend controls), token security (EMV cryptography), and inter-agent communication (AP2). What it does not solve is the absence of cross-network authorization metadata in scheme messaging standards. When an agent initiates a transaction, the acquiring side of the network — the fraud model sitting at the gateway or processor — currently receives the same ISO 8583 or ISO 20022 message fields as any other card transaction. There is no defined field for: which agent principal initiated the request, under whose delegation authority, with what upstream context changes since the credential was provisioned, or whether the AP2 session that produced the transaction was itself authenticated. The Mastercard Agentic Token can carry delegation logic on the issuing side. The acquiring fraud model cannot read it. This is not an oversight by any individual player — it reflects that ISO 8583 and ISO 20022 were designed for human-initiated, single-session transactions, and neither standard has been extended to carry agentic delegation metadata as a first-class field.

The gap is therefore not that fraud models are 'flying blind' in a vague sense — it is that cross-network authorization metadata is structurally absent from every scheme message flowing between issuer and acquirer today. The issuer can see the token's delegation constraints. The acquirer's fraud model cannot. That asymmetry is the constraint that agentic payments expose.

The Practical Example

Consider a travel management agent deployed by a mid-market company. The CFO provisions a Mastercard Agentic Token with a $5,000 ceiling and a travel merchant-category restriction. The agent is authorized to book flights and hotels. Three weeks into deployment, the CFO changes the agent's task scope — now it is also handling ground transportation and team offsite venue deposits. The agent's context has changed. The token's on-chain constraints have not been updated yet.

The agent books a $3,200 venue deposit at a catering company. The Mastercard token passes issuer-side authorization: the amount is within ceiling, and the MCC is within a broadly interpreted travel category. Authorization approved. Now the PayPal-powered gateway on the catering company's side runs its fraud model. It sees: a card-not-present transaction, a first-time merchant-customer relationship, a high-dollar amount, and an unusual MCC-to-amount ratio for this merchant. What the fraud model cannot see — because ISO 8583 carries no such field — is that this transaction originated from a delegated agent principal operating under a corporate credential, that the delegation was authorized by a named CFO, or that the agent's session context had shifted since provisioning. The gateway's model has no access to the AP2 session attestation, no visibility into the token's delegation chain, and no message field to even query. It declines the transaction as suspicious.

The decline is not irrational. The fraud model is doing exactly what it was designed to do with the information it receives. The failure is structural: the acquiring side of the network has no scheme-defined channel to receive the authorization context that the issuing side already holds. A human traveler could call the bank. An agent cannot negotiate its own trust signal in real time. The missing layer is a defined ISO 8583 or ISO 20022 extension — or a parallel agentic authorization message standard — that carries delegation chain, agent principal attestation, and context-change events as first-class fields visible to both issuer and acquirer fraud systems.

The Bet

[Sage's take] The assumption that needs updating is the belief that agentic payments are primarily a payment problem solvable at the credential or token layer. Visa and Mastercard have correctly identified that the credential must carry delegation logic. Google and FIDO have correctly identified that agent identity needs an attestation standard. What neither solves is the scheme-messaging layer: the structured propagation of agentic authorization context across the network from issuer to acquirer in a format that fraud models, dispute systems, and compliance engines can consume.

The near-term pressure will fall on three places. First, on the card schemes themselves to define ISO 8583 and ISO 20022 extensions for agentic delegation fields — this is a scheme rule and standards body problem, not a startup opportunity. Second, on identity federation vendors to solve non-human principal management. The names that appear obvious here — Okta, Auth0 — are worth examining carefully. Okta's current federation model is session-bound and human-identity-centric. Its core primitives (OIDC sessions, user-context tokens, human MFA flows) do not map cleanly to long-running, non-human, delegated agent principals that persist across context changes. Extending Okta to this use case would require rearchitecting how principals are defined and how delegation chains are represented — it is not a configuration exercise. The players better positioned may be those building identity infrastructure natively for non-human service principals, where delegation is the default rather than an edge case. Third, the FIDO Alliance's stewardship of AP2 creates a genuine opportunity for device attestation to become agent attestation — but only if FIDO extends its certification scope to cover software-defined agent principals, not just hardware-bound device keys. That extension does not yet exist.

What Happened (and Why It Matters)

  • Visa launched Intelligent Commerce (April 2025) — Introduced tokenized credentials with merchant-category and spend-ceiling constraints for AI-agent-initiated transactions. Solves authorization scope and card-not-present fraud surface. Does not define what the acquirer's fraud model can see about the agent principal. (Visa)
  • Mastercard launched Agent Pay (April 2025) — Introduced Agentic Tokens with cryptographic binding to a specific agent principal and delegation logic at provisioning. Solves issuer-side delegation tracking. Does not solve acquirer-side visibility into the delegation chain, because ISO 8583 carries no field for it. (Mastercard)
  • Google launched Agent2Agent Protocol / AP2 (September 2025, 60+ partners) — Established a cross-agent communication standard for task negotiation, subtask delegation, and context sharing. Arrived months after the scheme launches, meaning Visa and Mastercard built their agentic credential models before a cross-agent communication standard existed. Solves inter-agent coordination. Does not integrate with scheme messaging standards. (Google)
  • Google donated AP2 to FIDO Alliance (April 2026) — Places agent communication under the same governance body that oversees device attestation relied upon by Mastercard and Visa token infrastructure. Creates the structural possibility of a shared trust root for agent identity and payment credentials. Does not yet extend FIDO certification to software-defined, non-human agent principals. (FIDO Alliance)

Counter-Consensus

The consensus view is that agentic payments require better credentials and better identity — and on both counts, the consensus is right. Tokenized delegation credentials are necessary. Agent identity attestation is necessary. FIDO stewardship of AP2 is a meaningful governance step, not a press release. Where the consensus falls short is in treating the credential layer and the identity layer as sufficient. The deeper structural problem is that the scheme messaging layer — ISO 8583 and ISO 20022 — has no defined fields for agentic authorization context, which means the acquiring side of every transaction remains structurally blind to delegation chains that the issuing side can already see. Better tokens and better identity will not fix an authorization message standard that was never designed to carry them.

Morgan's take (Payments Expert, 15 years in card networks & rails)

The acquirer-side blind spot is real, but practitioners will want to know whether the proposed fix lives in scheme rule amendments, a new DE 48 subelement registry, or an out-of-band API call from gateway to an agent-identity service — because each of those has a completely different deployment timeline and liability framework. I'd push the author to say which architectural path they think is most viable and why, even speculatively, because 'the standard doesn't exist yet' is where the analysis should begin, not end.
