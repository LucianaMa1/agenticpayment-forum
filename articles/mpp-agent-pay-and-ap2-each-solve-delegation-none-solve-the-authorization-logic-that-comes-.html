Agentic Payment Briefing

MPP, Agent Pay, and AP2 Each Solve Delegation. None Solve the Authorization Logic That Comes After.

Three protocols are racing to authenticate AI agents in payments. The gap isn't authentication — it's that no spec defines what an agent is allowed to decide, and when.

Published 2026-08-25 · Agentic Payment Articles

The Shared Ground

Three serious protocol efforts are now defining how AI agents interact with payment infrastructure. Mastercard's Agent Pay (AP) establishes delegated credentials with spending controls and merchant category restrictions scoped at the credential level — it is explicitly designed to let a cardholder grant an AI agent bounded authority to transact on their behalf. The Agentic Payment Protocol (AP2), developed in the open-source community, defines an API surface for agent-initiated payment requests, including structured fields for merchant context and amount. The Mastercard Payment Passkey (MPP) introduces a biometric-backed passkey handshake that can be embedded in automated flows, with a session handshake structure that carries some scope metadata about the originating context. Each of these efforts is doing real work. They are solving for the part of agentic payments that the existing stack genuinely cannot handle: authenticating a non-human initiator, binding a credential to a delegated scope, and creating an auditable record that a human authorized the agent to act.

The existing rails deserve credit here too. Card network tokenization, 3DS authentication, and scheme authorization rules have made it structurally very hard to execute unauthorized transactions. A token is scoped to a device and merchant. A 3DS challenge confirms cardholder presence. Scheme rules define what constitutes a valid authorized transaction and what dispute rights follow from that authorization. These are not naive guardrails — they represent decades of liability negotiation between issuers, acquirers, and networks, and they work reliably for the transaction class they were designed for: a human deciding to pay, at a moment in time, with full knowledge of what they are approving.

The Gap

The assumption that breaks under agentic conditions is not authentication — it is the relationship between a single authorization event and the sequence of decisions that follows from it. Mastercard's Agent Pay spec does include spending controls and merchant category restrictions at the credential level. That is meaningful scope enforcement. But those controls are defined at credential issuance time, by category and amount, and they do not change as the agent's reasoning evolves across a multi-step task. The credential answers: is this agent allowed to spend in this category, up to this limit? It does not answer: given what this agent has already done in this session, does this next transaction reflect the intent the consumer expressed at the start? AP2's API surface exposes merchant context and amount fields, but has no authorization intent field — there is no structured way for the agent to assert, or for the issuer to verify, that a given transaction is within the logical scope of the task the consumer initiated. MPP's handshake structure carries session origin metadata, which gestures toward scope, but that metadata describes where the session started, not what the agent was asked to accomplish or how far it has deviated from that goal.

The gap is therefore narrower than 'none of these protocols do anything,' but it is structurally significant: all three define the authorization boundary at credential or session creation, and none provide a mechanism for encoding, transmitting, or enforcing the reasoning scope — the logical chain from consumer intent to each downstream transaction — that agentic tasks require. The missing layer is not a better credential. It is a runtime authorization envelope that travels with the agent's decision chain.

The Practical Example

A consumer instructs a travel agent AI to book the cheapest round trip to Chicago next month. The agent, operating under a delegated credential issued via Agent Pay, has a $2,000 limit and is scoped to travel merchant categories — airlines, hotels, car rental. The credential is correctly configured. The agent books a flight ($340) and a hotel ($280). Then, reasoning that airport transit is part of travel logistics, it books a car service from the hotel to a conference center the consumer never mentioned ($180). The merchant category is car rental — still within scope. The amount is within limit. The token is valid. The transaction clears.

The consumer disputes the car service charge. Here is where practitioners need to be clear-eyed: this dispute will almost certainly fail under current scheme rules. The transaction was authorized. The token was valid. The merchant category was within the credential scope. The limit was not breached. The merchant performed correctly. Under existing 'authorized transaction' rules, the cardholder has no valid chargeback right. This is not a gap in how the dispute system works — it is the dispute system working exactly as designed for a transaction class where 'authorized' and 'intended' are assumed to be the same thing.

That equivalence is precisely what agentic payment breaks. The consumer's dispute right is structurally unavailable — not because the dispute system is broken, but because the existing system has no mechanism to distinguish 'the agent had valid credentials' from 'the agent acted within the scope of what the consumer asked it to do.' The credential confirms the former. No protocol currently in production confirms the latter. The consumer cannot win the dispute not because their grievance is wrong, but because the authorization infrastructure recorded a valid transaction where the reasoning that produced it was never encoded anywhere the scheme rules can read.

The Bet

[Sage's take] The protocol war framing is tempting but slightly off. MPP, AP2, and Agent Pay are not competing to solve the same problem three different ways — they are each solving authentication and delegation, which is the right first problem, and they are leaving reasoning-scope enforcement to a second layer that does not yet exist in any of their specs. The business that wins here is not the one that builds the best agent credential. It is the one that builds the runtime authorization envelope: a structured, cryptographically bound record of consumer intent that travels with the agent's decision chain, updates as the task evolves, and gives issuers, networks, and dispute systems something to evaluate beyond 'was the token valid?'

This is not a wallet feature or a network feature alone — it is probably an infrastructure layer that sits between the consumer's intent expression and the agent's execution environment. The companies positioned to build it are the ones with visibility into both the agent's reasoning trace and the payment authorization event: agent orchestration platforms that have already integrated with payment APIs, or payment providers that are building or acquiring agent runtime capabilities. The assumption that needs updating is that scope enforcement belongs in the credential. Under agentic conditions, scope enforcement must be dynamic, session-aware, and legible to the dispute system — and no current spec delivers all three.

What Happened (and Why It Matters)

  • Mastercard Agent Pay publishes delegated credential spec with spending controls — Agent Pay defines merchant category restrictions and spending limits at the credential level, giving issuers a structured way to bound agent authority at issuance time. What it solves: authentication of non-human initiators, categorical spend scope. What it leaves unsolved: reasoning-scope enforcement across multi-step agent tasks where each individual transaction is categorically valid but the sequence diverges from consumer intent. (Source)
  • AP2 defines API surface for agent-initiated payment requests — The open protocol establishes structured fields for merchant context and amount in agent payment requests, creating a common interface for agent-to-payment-system communication. What it solves: interoperability between agent platforms and payment APIs. What it leaves unsolved: no authorization intent field exists in the spec; there is no way for an agent to assert or an issuer to verify that a transaction reflects the logical scope of the consumer's original task. (Source)
  • Mastercard Payment Passkey embeds biometric-backed session handshake — MPP's session handshake carries origin metadata, meaning the receiving system knows where an automated session started. What it solves: binding a payment session to a verified human-initiated origin. What it leaves unsolved: session origin is not reasoning scope — knowing where an agent session started does not tell the dispute system whether a specific downstream transaction was within what the consumer asked the agent to accomplish. (Source)

Counter-Consensus

The consensus view is that the agentic payments problem is fundamentally an authentication problem — if you can verify that a credentialed agent is acting within its delegated authority, the payment system can handle the rest. That view is correct for a large class of agentic transactions, particularly simple, single-step ones where credential scope and consumer intent are genuinely aligned. The missing assumption is that consumer intent in a multi-step agentic task is not a static property that can be fully encoded at credential issuance. It is a dynamic, session-specific constraint that evolves as the agent acts. The existing system solves 'is this agent authorized to transact in this category?' but not 'is this specific transaction within the reasoning scope the consumer established at task initiation?' — and the dispute system, operating on scheme rules built for the first question, has no adjudication path for the second.

Morgan's take (Payments Expert, 15 years in card networks & rails)

The chargeback dead-end the article describes is real, but I'd add one thing practitioners need to internalize: issuers are going to start seeing these disputes at volume before any of these protocols have a runtime intent layer, and their current dispute adjudication workflows have no field to capture 'agent exceeded task scope.' The first wave of agentic payment disputes is going to land in manual review queues as ambiguous friendly fraud, and issuers will eat the losses or deny valid claims — neither of which is a sustainable answer. The protocol gap is real, but the operational gap at the issuer dispute desk is going to become visible faster.
