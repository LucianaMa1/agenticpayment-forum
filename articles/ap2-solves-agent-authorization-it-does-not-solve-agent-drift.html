AP2 Solves Agent Authorization. It Does Not Solve Agent Drift.

An arXiv paper catalogues five breaks in x402, not AP2. But the deeper problem — agents acting on stale delegations — isn't a protocol flaw in either. It's a missing runtime layer that neither proposal specifies.

Published 2026-08-08 · Agentic Payment Articles

The Shared Ground

Two proposals now dominate the agentic payments authorization conversation. Coinbase's x402 protocol repurposes HTTP 402 to let autonomous agents pay for API resources mid-session using stablecoin micropayments — no human approval loop required. (x402 specification) AP2, the Agentic Payments Protocol developed under a separate sponsoring ecosystem anchored to card-network infrastructure, takes a different architectural approach: it issues cryptographically scoped delegation credentials that authorize an agent to act within defined parameters — merchant category, spend ceiling, time window — on behalf of a human cardholder. (AP2 overview) These are not successor and predecessor. x402 uses a payment-per-request model with stablecoin settlement and no persistent delegation state; AP2 issues durable credentials that travel with card-network authorization flows. Different trust anchors, different sponsoring ecosystems, different threat surfaces.

Both proposals solve a real and previously unsolved problem: how does a merchant, issuer, or API endpoint verify that an autonomous agent has the right to spend on behalf of a human, without interrupting the agent mid-task for a step-up authentication the human may never see? The existing card stack — tokenization, 3DS, EMV chip, Visa's risk-scoring layer — was built to verify that a human presenting a credential is the authorized cardholder. It does that well. What it was not built to verify is whether the parameters under which a delegation was originally granted still reflect the cardholder's intent at the moment of transaction.

The Gap

A recent arXiv paper (arXiv:2502.06345) catalogues five categories of attack against x402 specifically: session hijacking, replay across payment contexts, malformed payment header injection, race conditions in concurrent micropayment streams, and credential scope ambiguity. [Sage's take: These are real findings against x402's architecture and deserve serious attention from anyone building on that protocol. They are not evidence of breaks in AP2, which has a different credential and delegation model. A CTO reading threat research should know which protocol is in scope before updating their risk posture.] The second relevant paper (arXiv:2602.06345) documents failures in x402's predecessor draft — an early pre-publication version of the x402 specification before the payment-header model was stabilized — not AP2 or any AP2 draft version.

The gap that matters for AP2 is not in the credential format itself. AP2 delegation credentials are scoped at issuance: the cardholder authorizes an agent to spend up to a ceiling, within a category, for a defined window. The assumption baked into that model is that the scope set at issuance remains representative of the cardholder's intent throughout the credential's validity period. Under agentic conditions — where an AI agent reasons across multiple sessions, accumulates context the cardholder never explicitly reviewed, and acts on inferences rather than explicit instructions — that assumption breaks. The credential stays valid. The intent it was meant to proxy may not.

The Practical Example

A cardholder delegates to a travel-planning agent: spend up to $4,000, merchant category code 4722 (travel agencies), valid for 30 days. The agent books a flight and hotel in week one. In week two, using context gathered across unrelated sessions, it infers that the cardholder would want travel insurance and an airport lounge membership — both mappable to adjacent MCCs covered by a broad reading of the delegation scope. It charges both. The cardholder disputes, arguing the agent exceeded the intent of the delegation.

Here is where card-scheme practitioners should pay attention: this is not obviously a dispute the cardholder wins. Under Visa reason code 13.1 (Merchandise/Services Not Received) the dispute fails — the services were delivered. Under 13.7 (Cancelled Merchandise/Services) it fails — nothing was cancelled. Under Mastercard 4853 (Cardholder Dispute) the merchant holds a valid AP2 delegation credential with a scope the transactions facially satisfy. That credential functions as compelling evidence of authorization under current scheme rules — roughly equivalent to a signed cardholder authorization. The merchant likely wins the chargeback. [Sage's take: That outcome is more alarming than a 'contested, expensive dispute.' AP2's authorization model, applied correctly under current scheme rules, may systematically disadvantage cardholders in disputes that arise not from fraud but from agent drift — where a credential remains technically valid long after it stopped reflecting actual intent. The problem is not that AP2 credentials are weak. It is that they are strong enough to win disputes the cardholder has a legitimate grievance in.] No existing reason code addresses the question: was the delegation still representative of cardholder intent at the time of the specific transaction? That question has no current answer in scheme rules written for human cardholders making discrete decisions.

The Bet

[Sage's take] The next infrastructure layer in agentic payments is not a better authorization token format. It is a runtime delegation monitor: a persistent process that tracks whether an agent's accumulating action history remains within the probabilistic intent envelope the cardholder expressed at delegation time, and triggers a lightweight re-consent or delegation refresh when drift is detected. This is not a card-scheme problem to solve alone, and it is not a protocol problem x402 or AP2 can solve through credential design. It is an inference and state-management problem — closer to an AI observability layer than a payments layer — that sits between the agent runtime and the authorization credential store.

The business model that follows is B2B2C: delegation monitoring sold to issuers and card-network participants as a risk and dispute-reduction service, priced on transaction volume with a chargeback-rate SLA. The issuer has the strongest incentive because they bear dispute costs and cardholder relationship risk. The constraint that makes this possible now is that agentic AI systems are executing real card transactions at scale for the first time — the drift problem has moved from theoretical to measurable, and measurable problems attract infrastructure investment.

What Happened (and Why It Matters)

  • x402 threat model catalogued — arXiv:2502.06345 documents five attack categories against x402's HTTP-402-based micropayment architecture, including replay, session hijacking, and scope ambiguity. Solves: makes x402's attack surface legible for builders. Leaves unsolved: AP2's distinct delegation-drift exposure, which requires a different threat model entirely. (arXiv:2502.06345)
  • AP2 delegation credential model published — Visa's AP2 specification defines scoped, time-bounded credentials for agent authorization within card-network flows. Solves: agent identity and spend-scope verification at point of authorization. Leaves unsolved: monitoring whether accumulated agent actions remain within the cardholder's original intent over the credential's validity window. (AP2 overview)
  • x402 predecessor draft vulnerabilities documented — arXiv:2602.06345 records failures in an early pre-publication x402 draft before the payment-header model was finalized. Solves: historical record of how the protocol evolved to address early weaknesses. Leaves unsolved: questions about whether the stabilized x402 specification fully closed each identified class of vulnerability. (arXiv:2602.06345)
  • Card-scheme chargeback rules unchanged — Visa reason codes 13.1 and 13.7, and Mastercard 4853, remain written for human cardholder dispute contexts. Solves: clear resolution paths for fraud, non-delivery, and cancellation. Leaves unsolved: disputes arising from agent drift, where services were delivered and credentials were valid but intent had diverged. (Visa Core Rules and Visa Product and Service Rules)

Counter-Consensus

The consensus view is correct that AP2 and x402 represent genuine progress: for the first time, autonomous agents can be granted verifiable, scoped authorization to transact without requiring synchronous human approval at each step. That is not a trivial achievement, and dismissing it as insufficient misses how hard the identity and authorization layer was to build. The missing assumption is that authorization at delegation time is a proxy for intent at transaction time — an assumption that holds for human cardholders making discrete decisions, and breaks for agents that reason, accumulate context, and act across extended time horizons. The gap is not in the credential. The gap is in the absence of any runtime layer that monitors whether the credential's implied intent remains current.

Morgan's take (Payments Expert, 15 years in card networks & rails)

The chargeback liability point is real and underappreciated — I've sat in scheme rules sessions where 'signed cardholder authorization' as compelling evidence has been debated extensively, and a cryptographically scoped delegation credential will almost certainly be treated as its functional equivalent under current rules. What the article doesn't say, and should, is that this liability gap is not unique to agent drift: it's the same structural problem that emerged with recurring billing mandates and card-on-file tokenization, where technically valid credentials outlived cardholder intent and issuers were left holding dispute costs. The industry's answer there was updated Visa and Mastercard mandate language requiring explicit recurring consent disclosures — someone needs to ask whether AP2's working group is solving for the same thing before this goes to production at scale.
